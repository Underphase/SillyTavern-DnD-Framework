# SillyTavern · D&D Framework

Автор: **Underphase**. Расширение для **SillyTavern 1.18.0**: свободные правила ролевой игры, память текущего чата, персонажи из RPG API и настоящие броски кубиков во время ответа модели.

## Установка

В SillyTavern открой **Extensions → Install extension** и вставь:

```text
https://github.com/Underphase/SillyTavern-DnD-Framework
```

Перезагрузи страницу. На экране появится лунная кнопка **☾**. Её можно перетаскивать; обычное нажатие открывает окно по центру экрана. Настройки также доступны из списка расширений. Сборка, npm и серверные плагины для установки расширения не нужны.

В этом репозитории находится только расширение. Backend устанавливается отдельно: [dnd-api](https://github.com/Underphase/dnd-api).

## Первое подключение

1. Запусти свой обновлённый RPG API на порту **8001**. Порт 8000 обычно занят SillyTavern.
2. Открой чат и **☾ → Настройки**. Укажи адрес RPG API и ключ, если он включён на backend. Нажми **Проверить API**.
3. Для отдельной ИИ выбери собственный OpenAI-совместимый endpoint, ключ и модель либо **профиль SillyTavern**. Профиль отправляет запросы через сервер ST и подходит для провайдеров, запрещающих браузерные CORS-запросы. Основное подключение повествования при этом не переключается.
4. Сохрани настройки и нажми **↻ Обновить**. Персонажи и память будут извлекаться из сообщений, затем автоматически обновляться после ответов.
5. Для бросков включи **Enable function calling** в настройках ответа SillyTavern и используй основную модель с поддержкой инструментов. Отдельная ИИ не заменяет поддержку инструментов основной моделью.

Параметры подключения общие. Персонажи, выбор героя, секции, сводка, факты, значения и определения треккеров относятся к конкретному чату. Новый чат, в том числе ответвление с копией метаданных, получает новую область backend и новое состояние. Шаблон секций/треккеров можно сохранить в настройках для будущих чатов. Персонажей из прежнего API можно импортировать по `owner_id`; создаётся отдельная копия.

### Выбор модели из списка

В **Настройки → Отдельная ИИ** нажми **OpenRouter**, чтобы подставить его адрес и загрузить каталог, либо введи адрес своего API и нажми **Загрузить модели**. Используется `GET /models` относительно адреса API; для OpenRouter — [его каталог моделей](https://openrouter.ai/docs/api/api-reference/models/get-models).

Список прокручивается и поддерживает выбор клавиатурой. Поиск фильтрует названия и ID без учёта регистра, например `claude`, `gemini` или `:free`. Нажми на модель и затем **Сохранить настройки**. Поиск не вызывает ИИ и не расходует токены. Название также можно ввести вручную, если провайдер не предоставляет каталог или запрещает браузерные запросы. В режиме профиля модель берётся из выбранного профиля ST.

### Телефон и backend на ПК

Если ST работает на самом телефоне, в адресе RPG API укажи **локальный IP компьютера**, например `http://192.168.1.10:8001`. `127.0.0.1` на телефоне означает сам телефон. Оба устройства должны иметь сетевой доступ друг к другу; backend должен слушать интерфейс сети, а его порт — быть доступен через брандмауэр.

В `CORS_ORIGINS` backend добавь **origin страницы ST**: протокол, хост и порт без пути. Например, для ST в Termux это может быть `http://127.0.0.1:8000`. Если открываешь ST на ПК через телефон — это может быть `http://192.168.1.10:8000`. Страница ST через HTTPS требует доступного через HTTPS backend: браузер блокирует смешанный контент.

GitHub распространяет код расширения, но не запускает Python API. Для доступа извне сети нужен отдельно размещённый backend или настроенный сетевой доступ. Перед внешним доступом задай ключ API и точный список разрешённых origins. Текущий API — для одного доверенного владельца; `scope_id` разделяет истории, но не является авторизацией разных пользователей.

### Если соединение не работает

`Failed to fetch` означает отсутствие доступного браузеру HTTP-ответа; это не проверка правильности ключа. В версии 0.1.2 сетевые ошибки поясняются в окне, а при включённом **Dev mode** журнал показывает origin страницы ST, адрес запроса без секретов, статус (или его отсутствие), длительность и подсказки по CORS/сети. Проверка неправильного ключа отдельно показывает HTTP 401. Браузер не позволяет однозначно отличить CORS от отказа соединения через JavaScript.

При ST на телефоне и backend на ПК адрес ST может оставаться `http://127.0.0.1:8000`, но адрес RPG API должен указывать на IP компьютера. Backend, запущенный только с `--host 127.0.0.1`, не принимает подключения с телефона: используй его сетевой адрес в `--host` или `0.0.0.0`. Оба устройства должны находиться в доступной друг для друга сети.

## Повествование и проверки

Главный герой выбирается **один**: персонаж API, пользователь или имя любого бота/персонажа вручную. ИИ может предложить кандидата; выбор применяется после подтверждения кнопкой. До выбора действует ансамблевое повествование. Пользователь не назначается ГГ автоматически.

Основная модель вызывает `rpg_check` в штатном цикле tool calling ST и получает результат до продолжения повествования. Расширение не рассчитывает случайность и не ускоряет весь бой одним инструментом. Инициатива, действия и урон могут быть отдельными проверками с подробным повествованием между ними.

Backend:

- бросает `NdS` через криптографический генератор `secrets.randbelow`;
- рассчитывает бонус характеристики по выбранному правилу (`d20`: `(score−10)//2`, `raw`: сам показатель, `none`: без характеристики);
- берёт сложность из сохранённого `target_id` + `difficulty_path` (например, `armor_class`) либо принимает явную сложность с обоснованием для свободного события;
- добавляет целые бонусы из сохранённых путей вроде `skills.lockpick.bonus`;
- поддерживает преимущество/помеху для `1d20`, сравнение `>=` или `<=`, событийные `1d100` и произвольные кубики в пределах лимитов API;
- до броска фиксирует причину, сложность и её обоснование;
- сохраняет результат до возврата модели; повтор того же события, персонажа и `check_key` не перебрасывает кубик;
- отклоняет изменённые параметры уже решённой проверки с HTTP 409.

Для гарантированного пассивного успеха навык должен иметь явную структуру, например:

```json
{"skills":{"divine_locksmith":{"automatic_success":true,"actions":["open:astral_gate"]}}}
```

Тогда `resolution="automatic"`, `passive_path="skills.divine_locksmith"` и `check_key="open:astral_gate"` дают успех без броска. Невозможность задаётся `resolution="impossible"` с причиной. Сила персонажа и названия навыков не ограничены редакцией D&D.

**Граница гарантий:** backend защищает случайное число, сохранённые параметры и повторы с тем же идентификатором. Смысл действий, необходимость проверки, начальная сложность, соответствие свободного навыка ситуации и добросовестное использование нового `check_key` по-прежнему зависят от модели/правил. Промпт не может математически гарантировать, что модель всегда вызовет инструмент. Если function calling недоступен, расширение сообщает об этом; фиктивные результаты не подставляются. Продолжения, impersonation и quiet-запросы имеют ограничения самого ST.

## Память и расход токенов

Обработчик получает новые/изменённые/удалённые события, сводку, подходящие факты, индекс персонажей и подробности участвующих персонажей. Пустые поля исключаются. Новые события разбиваются на пакеты; отдельное длинное сообщение сохраняется целиком, поэтому бюджет событий мягкий. Полная история не пересылается на каждом ответе.

Факты со стабильными ID остаются в метаданных чата; новые ответы исправляют или дополняют их. Основная ИИ получает компактный контекст, а через `rpg_recall` может найти старые факты и полные данные персонажа. Вкладка **Память** позволяет редактировать сводку, факты и закрепление. Алгоритмический поиск по словам не гарантирует идеальный выбор воспоминаний; важные сведения можно закрепить.

После редактирования, удаления или смены варианта сообщения обработчик видит коррекцию и согласует данные через API. Это семантическое исправление ИИ, а не механический откат всей базы. Хранятся текущее и предыдущее состояния. Незавершённая синхронизация сохраняется в чате и повторяется с тем же ID без повторного создания персонажей. Ответ устаревшего запроса отбрасывается, если чат или сообщения изменились.

**Dev mode** показывает время обработки, размеры запросов и `usage`, когда его отдаёт провайдер. Символы не выдаются за токены. Ключи не добавляются в память чата или подсказки модели.

## Свои интерфейсы

В **Мастерской** можно описать механику ИИ или самостоятельно редактировать промпт, HTML, CSS и определения полей. Нажатие **Создать с ИИ** создаёт черновик. Сохранение происходит отдельно; **Отмена** не меняет активный треккер.

В HTML используются `{{field_id}}`. Доступны виджеты:

| `type` | Представление |
|---|---|
| `text` | Текст |
| `number` | Число |
| `meter` | Значение и шкала до `max` |
| `inventory` | Список предметов |
| `coins` / `gems` | Монеты / кристаллы |
| `boolean` | Да / нет |

Источники `ai`, `character`, `scene`, `turns`, `clock` определяют обновление. `character` и `scene` используют `path`, например `current_hp` или `party.name`. `character` связан с выбранным персонажем API либо первым персонажем. `turns` — число обработанных ответов, `clock` — местное время устройства, которое обновляется при открытом интерфейсе. Эти источники не требуют отдельных запросов ИИ. Игровое время в сцене отличается от часов устройства.

Предпросмотр отображает вымышленные `value` из определения поля. Они **не записываются** как реальные данные чата. Свои стили и HTML работают в изолированном iframe с CSP: JavaScript, внешние ресурсы и доступ к интерфейсу ST запрещены. Это конструктор представлений и декларативных источников, а не выполнение произвольного сгенерированного кода.

## Разработка и проверки

```sh
node --test tests/core.test.js
```

`tests/browser.mjs` проверяет интерфейс через Playwright в тестовом окружении с подставными ответами API/ИИ. Укажи путь к установленному Playwright в `PLAYWRIGHT_MODULE`; при необходимости `BROWSER_CHANNEL=msedge` или `chrome`. Скриншоты записываются в игнорируемый каталог `test-results`.

Интеграция сверена с исходниками [SillyTavern 1.18.0](https://github.com/SillyTavern/SillyTavern/tree/1.18.0) и [документацией function calling](https://docs.sillytavern.app/for-contributors/function-calling/). По просьбе автора изучен [Multihog D&D Framework](https://github.com/MultihogAurelius/SillyTavern-MultihogDnDFramework) как пример организации расширения. Реализация этого проекта самостоятельная; код, стили и промпты примера не перенесены.

Проверена также загрузка в отдельной настоящей установке ST 1.18.0: открытие чата, создание метаданных расширения, вызов реального RPG API через штатный `ToolManager`, повтор проверки без переброса и сохранение результата в чате. Автоматический обработчик в браузерных тестах использует подставной ответ модели; качество повествования и поведение конкретного провайдера нужно проверить с выбранной пользователем моделью.
